# Ritualvision 작업 기록 (2026-11-10 ~ 11-12)

USB 카메라로 Ritualvision을 돌리면서 생긴 문제와 해결 과정을 기록합니다. 각 항목은 **증상 → 원인 → 해결 → 확인** 순서입니다.

- 설계 기준: `ritual_vision.pdf` (V2 접힌 선 + 엣지 대시)
- 실물 기준: `stl_hexcell` (3D 프린트 타일 A_001 ~ D_004, 25개)
- 카메라: 일반 USB 카메라(카메라 0, DirectShow, 1280x800). oCam(oCam-1MGN-U-T2)도 연결되어 있지만 쓰지 않습니다.

---

## 1. 초당 프레임 수가 10fps

**증상**: `camera.xml`에 `fps="60"`을 설정했는데도 실제로는 10fps였습니다.

**원인**: DirectShow는 해상도를 설정하는 순간 영상 포맷을 비압축(YUY2)으로 되돌립니다. 코드는 MJPG(압축)를 해상도보다 **먼저** 설정해서 MJPG 설정이 사라졌습니다. 그래서 비압축 1280x800 영상이 USB 2 대역폭에 막혀 10fps가 되었습니다.

**해결**: `camera.py`에서 MJPG 설정을 해상도·fps 설정 **뒤로** 옮겼습니다.

**확인**: 같은 카메라에서 10fps → 약 55fps.

## 2. 60fps에 못 미침 (인식 처리 속도)

**증상**: 1번을 고친 뒤에도 55fps 근처에서 멈췄고, 창을 띄우면 52fps였습니다.

**원인**: 마커 인식에 프레임당 약 18ms가 걸렸습니다(60fps가 되려면 16.6ms 이하). 창을 띄우면 화면 그리기 약 3ms가 같은 루프에 더해졌습니다.

**해결**
- `recognizer.py`: 이진화와 후보 검사에서 불필요한 복사·형변환을 없앴습니다(16.6 → 13.4ms). 저장된 프레임에서 결과(마스크·마커)가 기존과 완전히 같은지 확인했습니다.
- `main.py`: 창 모드에서는 인식 → 추적 → TUIO 송신을 별도 스레드(`Pipeline`)로 분리했습니다. 이제 화면 그리기가 추적 속도를 깎지 않습니다. 창 없이 실행(`-n`)과 `--once --json`은 예전처럼 동기 방식입니다.

**확인**: 창 없이 약 65fps, 창 모드 약 64fps. 이후 다른 수정까지 더해 현재 약 80~87fps입니다(카메라가 60fps보다 빠르게 보내 줌).

> 1·2번은 커밋 `fb75bc0`(브랜치 `feat/tension`, 푸시됨)에 들어 있습니다. 이 커밋에는 oCam SDK 대체 경로(`ocam.py`)도 함께 들어 있습니다.

## 3. 마커가 빨간색 — 처음 가설: 크기 제한

**증상**: 선(blob)은 잘 잡히는데 마커가 빨간색으로 표시되었습니다. 빨간색은 "접힌 선은 찾았지만 대시 코드가 ID 표에 없음"이라는 뜻입니다.

**조치**: 카메라에 보이는 마커 크기를 고정값으로 설정했습니다. 실제 프레임 300장에서 잰 rc(접힌 선 팔 길이)는 68px였고, `ritualvision.xml`에 `size_ref="68.00"`, `size_on="true"`, ±10%를 적용했습니다.

**결과**: 크기 제한은 원인이 아니었습니다(당시 크기 제한은 꺼져 있었음). 크기가 틀린 노이즈 접힌 선을 걸러내는 효과만 있습니다. 진짜 원인은 아래 4~6번입니다. 크기 범위는 7번에서 다시 조정했습니다.

## 4. 설계(PDF) · STL · 코드 비교

**결론**: 셋은 서로 맞습니다. 틀어진 곳은 카메라 영상이 좌우로 뒤집혀 있다는 점(5번)뿐입니다.

| 항목 | PDF | 코드 / 데이터 | STL 25개 |
|---|---|---|---|
| 구조 | 접힌 선 1개 + 네 변 대시 (UR 0–3, R 1–3, LR 1–3, LL 0–3) | 같음 | 같음. 선이 다리처럼 솟아 유리에 닿음 |
| 인식 단계 | 이진화(창 15, 기준 12) → 접힌 선 → O = C + rc·(u₁+u₂) → 대시 → 각도 → ID | 수치까지 같음 | – |
| 회전값 | θ = θcorner − 210° | 같음 | – |
| 전시용 ID | 0–24, 25개 | `ids.json` id 0–24 | A_001…D_004가 **아래에서 볼 때** id 0…24에 순서대로 정확히 대응 |
| 오류 감지 | 대시 하나가 빠지면 표에 없는 코드가 됨 | id 0–24(그리고 0–59 전체)가 이 조건을 지킴 | – |

**PDF와 다른 점**
- **타일 테두리 위치**: PDF는 타일 외곽선이 0.99 rc에 있다고 가정했습니다. STL에서는 **0.938 rc**입니다. 대시 탐색 범위 안쪽이라 6번 문제의 원인이 되었습니다.
- **대시 위치**: STL에서는 0.839–0.888 rc입니다(PDF: 0.866–0.90 rc).
- **추가 ID**: `ids.json`에 PDF에 없는 id 25–59(35개)가 추가되어 있습니다. 이 ID들의 STL은 없습니다.

## 5. 카메라 영상이 좌우 반전 → 모든 코드가 거꾸로 읽힘

**증상**: D_001(id 21, 코드 2321)이 `1232`로 읽혀 빨간색이 떴습니다. 가끔 대시 하나를 놓치면 `1222` = **id 11**로 잘못 읽혀 초록색이 떴습니다.

**원인**: 타일은 선을 다리 삼아 유리 위에 섭니다. 그래서 테이블 아래 카메라는 타일의 진짜 밑면(윗면의 거울상)을 봐야 합니다. 그런데 이 USB 카메라는 영상을 스스로 좌우 반전해서 보냈습니다. 반전된 상태에서는 "대시 하나가 빠지면 표에 없는 코드"라는 오류 감지도 작동하지 않습니다.

**해결**
- `camera.xml`의 `<settings ... mirror="true">`에서 반전을 켭니다. ROI를 자른 다음 영상을 좌우로 뒤집고, 인식·미리보기·TUIO 좌표가 모두 뒤집힌 영상을 씁니다.
  - 관련 코드: `config.py`(`mirror` 읽기), `camera_options.crop`(반전), `main.py`(시작 로그에 `mirrored left-right` 표시)
- `<settings>` 안에 둔 이유는 전시 서버가 `camera.xml`을 다시 쓸 때도 `<settings>` 속성은 보존하기 때문입니다(`tracker/engines/base.py`로 확인).

**확인**: 저장된 프레임에서 `1232` → `2321` = **id 21**. 대시를 놓친 프레임은 `2221`(표에 없음)이 되어 오인식 대신 거부됩니다.

## 6. 타일 테두리가 선으로 잡힘

**증상**
- (a) 타일을 화면 아래쪽에 두면 마커를 아예 찾지 못했습니다.
- (b) 대시가 없는 변이 있는 타일(id 0–8, A_001–B_003)은 렌더 시험에서 빈 변에 대시가 1개 있는 것으로 읽혔습니다.

**원인**: 밝은 테이블 앞에서는 회색 타일의 테두리도 "주변 평균보다 어둡다"는 이진화 기준을 통과합니다.
- (a) 꼭짓점에서 1~2px 굵기의 테두리가 접힌 선 끝과 대시를 이어 붙였습니다. 하나로 이어진 3개짜리 선은 "두 팔이 120°로 만나는 접힌 선"이 아니라서 접힌 선을 찾지 못했습니다.
- (b) STL의 테두리는 0.938 rc에 있어서(4번 참고) 대시 탐색 범위(0.94 rc 미만) 안에 들어와 대시로 세어졌습니다.

**해결** (`recognizer.py`의 `binarize`)
- 테두리 픽셀의 밝기는 101–130으로 **타일 면(115–130)과 같은 수준**이고, 진짜 선은 55–90입니다.
- 그래서 "주변 평균보다 어두움"에 더해 "주변에서 가장 어두운 평균값(= 타일 면)보다 `FACE_MARGIN`(4) 이상 어두움"도 만족해야 선으로 인정합니다.
- 여유값은 0/4/8/12를 비교해 4로 정했습니다. 0~4는 모든 선을 유지하고, 8 이상은 일부 선을 놓칩니다.

**중간 과정**: (b)를 먼저 대시 탐색 범위를 0.91 rc로 좁혀 막았습니다. 테두리 조건이 들어간 뒤로는 범위를 넓혀도 테두리가 잡히지 않아서, 7번에서 다시 넓혔습니다.

**확인**: 화면 아래쪽 실패 프레임 0/4 → 4/4, STL 렌더(25종 × 크기 3가지) 43/75 → 75/75. 예전 종이 마커 스냅샷은 그대로였습니다(34/44, 오인식 0).

## 7. 화면 좌우 끝에서의 인식

**증상**: 마커를 오른쪽 끝에 두면 300장 모두 빨간색이었습니다(코드 `2311`/`2301`).

**원인**
- 광각 렌즈 왜곡 때문에 접힌 선에서 먼 쪽 대시가 바깥으로 밀려 **0.917–0.943 rc**에 찍혔습니다. 6번 중간 과정에서 0.91로 좁힌 범위 밖입니다.
- 같은 타일의 rc도 위치에 따라 달랐습니다. 오른쪽 끝 62, 가운데 64, 아래쪽 66–70, 왼쪽 끝 65–66px입니다. 그래서 68px ±10% 범위에서는 오른쪽 끝이 하한에 걸렸습니다.

**해결**
- 대시 탐색 범위의 위쪽 끝을 **0.95 rc**로 정했습니다. 테두리는 6번의 이진화 조건으로 이미 걸러집니다. 0.91/0.94/0.95/0.96/0.97/1.00을 비교해, 다른 시험 세트를 해치지 않으면서 가장자리가 가장 좋은 값을 골랐습니다.
- 크기 범위를 **66px ±12%**(58.1–73.9px)로 넓혔습니다(`ritualvision.xml`).

**확인** (실제 카메라, 300프레임씩, id 21)

| 위치 | 수정 전 | 수정 후 |
|---|---|---|
| 오른쪽 끝 | 0/300 | **287/300 (96%)**, 나머지는 거부(오인식 0) |
| 왼쪽 끝 | – | **300/300** |
| 가운데 | 60/60 | 60/60 |
| 화면 아래쪽 | 0/4 | 4/4 |

- 다시 빌드한 exe로 확인: `mirrored left-right`, `size 66.0px -12%/+12%`, `markers [21]`, 약 87fps.
- 프레임당 인식 시간은 약 10ms입니다.

# 2026-11-12 — 전시 IR 환경

전시 세팅: 카메라에 IR 필터, 테이블 가장자리에 IR 다이오드(12x2, 8x2). 카메라는 USB 카메라(VID 0C45 / PID 636D), 회색 영상, 실제 약 116fps.

이 환경에서는 **타일이 밝고 배경(테이블 위 공간)이 어둡습니다.** 3~7번은 반대 조건(밝은 테이블, 회색 타일)에서 맞춘 것이라 아래 문제가 생겼습니다.

## 8. IR 환경에서 마커가 전혀 안 잡힘

**증상**: 선은 눈에 보이는데 검출 0건.

**확인**: 카메라 옵션 26가지 조합(노출 -9~-3, 게인 0~64, 대비 0~64, 감마 72~400, 선명도 0~6, 밝기 ±40, 역광보정 0~3)을 12프레임씩 녹화해 돌렸고, 모든 조합에서 0건이었습니다. 옵션 문제가 아닙니다.

**원인**: 6번에서 넣은 "타일 면보다 `FACE_MARGIN` 이상 어두워야 선" 조건입니다. 이 조건은 주변에서 가장 어두운 평균값을 타일 면으로 봅니다. IR에서는 배경(약 36)이 선(25~45)만큼 어두워서 배경이 "면"이 되고, 선이 배경보다 더 어두워야 통과하게 됩니다.

**해결**: 조건을 스위치로 만들었습니다. `camera.xml`의 `<settings ... face_check="false">`로 끕니다(기본 true = 예전 동작).
- `recognizer.py`(`Recognizer.face_check`), `config.py`(`CameraConfig.face_check`), `main.py`(시작 로그)
- `<settings>`에 둔 이유는 5번의 `mirror`와 같습니다(전시 서버가 보존).

**확인**: 가장 밝은 타일(id 23)이 12/12 프레임에서 읽힘. 어두운 타일 둘은 아직 안 읽힘 → 9번.

**카메라 옵션에 대해 알게 된 것**
- 노출은 -7에서 막힙니다(-6 이상은 밝기 동일). `fps="60"`을 요청해도 카메라가 약 116fps로 돌아 프레임 시간이 한계입니다.
- 게인은 0~64 어디에 둬도 밝기가 변하지 않습니다.
- 초점 제어는 안 됩니다(`focus` 설정 실패).
- 범위: 밝기 -64~64, 대비 0~64, 게인 0~64, 선명도 0~6, 감마 72~500, 역광보정 0~3.

## 9. 면 조건을 끈 뒤 감지가 튐

**증상**: 감지는 되지만 ID가 깜빡이고 가끔 엉뚱한 ID가 나옴. 정지 타일 3개, 240프레임 기준 id 10: 96/240, id 23: 232/240, id 21: 191/240, 잘못된 ID 2건(id 2 등).

**원인 1 — 타일 외곽선이 선으로 잡힘**: "주변 평균보다 어두움" 조건만 남자, 밝은 타일 옆 어두운 배경의 경계가 육각형 선으로 한 겹 더 나타났습니다. 이 선이 대시로 세어지고(`1120` → `1121`), 외곽선 꼭짓점(120°, 두 팔 길이 같음)이 가짜 접힌 선이 되었습니다.

**원인 2 — 접힌 선 크기를 두 팔 평균으로 계산**: 어두운 타일에서 한쪽 팔 끝이 흐려져 짧게 잡히면 rc가 66 → 58px로 줄고, 중심이 어긋나 대시가 탐색 범위를 벗어납니다(코드 `0000`).

**해결 1 — 밸리 방식 선 판정** (`recognizer.py`의 `_valley`, 스위치 `camera.xml` `<settings ... valley="true">`)
- 선 = 양쪽이 밝은 가는 어두운 줄. 영상의 닫힘 연산(9px 창, 가는 어두운 줄을 메운 밝기)보다 `offset`% 이상 어두운 픽셀입니다.
- 폭 8px까지의 선은 메워지고, 넓은 어두운 배경은 메워지지 않아 선이 되지 않습니다.
- 임계값이 회색 단계가 아니라 %인 이유: 타일마다 조명이 다릅니다(같은 프레임에서 면 밝기 131 / 165 / 199).
- **`valley="true"`일 때 `ritualvision.xml`의 `offset`은 %로 읽힙니다.** 8/10/12/14/16/20을 비교해 12~14가 가장 좋았습니다(8과 20은 어두운 타일을 놓침).
- 이 방식에서는 `face_check`와 `block`을 쓰지 않습니다.

**해결 2 — 긴 팔 기준 재시도** (`recognizer.py`의 `process`)
- 두 팔 평균으로 ID가 안 나오고 긴 팔이 평균보다 4% 이상 길면, 긴 팔 길이를 rc로 잡아 한 번 더 읽습니다.
- 대시 하나가 빠지면 표에 없는 코드가 되므로(4번), 이 재시도가 한 마커를 다른 마커로 바꾸지는 않습니다.

**접힌 선 조건 점검** (조건별 탈락 집계)

| 조건 | 판정 |
|---|---|
| 두 팔 길이 비 0.75~1.33 | 유지. 0.33~3.0까지 풀어 봐도 검출이 늘지 않음. 탈락은 대부분 외곽선 조각 |
| rc = 두 팔 평균 | 수정 (해결 2) |
| 꺾임 각도 120° ±6 | 유지. 진짜 접힌 선은 118~122° |
| 분산비 4~40, 굵기, 팔당 픽셀 수 | 유지. 진짜 접힌 선을 떨어뜨린 사례 없음 |
| 중심이 겹치면 rc 큰 쪽 채택 | 유지. 단, 외곽선과 붙은 큰 접힌 선을 우선하므로 크기 필터를 켜는 것이 안전 |

**확인** (같은 녹화본 240프레임, offset 12%)

| 타일 | 수정 전 | 수정 후 |
|---|---|---|
| id 10 (왼쪽, 어두움) | 96 | 225 |
| id 23 | 232 | 240 |
| id 21 | 191 | 240 |
| 잘못된 ID | 2건 | 0건 |

- 실제 카메라 15초(정지 타일 4개, id 10·21·23·24): 260회 확인 모두 검출, 위치 흔들림 0.003 이내, 약 92fps.
- 예전 스냅샷 11장, 기본 방식(`valley="false"`): 유효 34건으로 변화 없음.
- **움직이는 타일은 확인하지 않았습니다.**

## 10. IR 환경 HW 보완 (미적용, 제안)

- IR LED가 카메라에 직접 보이지 않게 가리기(차광 갓, ROI). 유리에 비친 LED 점이 타일 옆에 밝은 점으로 찍힙니다.

## 남은 일 · 주의

- **전시 서버가 설정을 덮어씀**: 서버는 웹 UI 설정(`rv_size_*`)으로 `ritualvision.xml`을 다시 씁니다. 서버로 돌리면 위 크기 범위가 서버 값으로 바뀌므로, 웹 UI에서도 같은 값(66px, ±12%)으로 맞춰야 합니다. `camera.xml`의 `mirror`는 서버가 보존합니다.
- **실제 카메라로 확인한 타일은 D_001(id 21) 하나뿐**입니다. 대시가 없는 변이 있는 id 0–8(A_001–B_003)은 STL 렌더로만 확인했습니다.
- 화면 위·아래 끝과 네 모서리는 따로 재지 않았습니다. 오른쪽 끝 4%는 아직 거부되는데, 추적기의 `hold="3"`(놓친 마커를 3프레임 유지)이 짧은 끊김은 메워 줍니다.
- 오른쪽 끝에서 크기 범위 밖 접힌 선(노이즈)이 300프레임당 12~13개씩 걸러지고 있습니다. 정상 동작입니다.
- oCam SDK DLL(`vendor/ocam/libCamCap-x64.dll`)은 저장소에 올리지 않았습니다.
- **크기 필터가 꺼져 있습니다**: 서버 설정의 기준 크기가 0입니다. 웹 UI에서 접촉 측정을 하거나 약 66px를 넣어야 가짜 접힌 선을 더 걸러냅니다.
- **`hold="3"`은 116fps에서 약 26ms**입니다. 어두운 타일은 프레임의 약 6%를 놓치므로 10~12로 올리면 깜빡임이 줄어듭니다.
- 밸리 방식은 프레임당 약 11~15ms로, 카메라의 116fps를 다 따라가지는 못합니다(약 92fps).
- 가시광·밝은 테이블로 돌아가면 `valley="false" face_check="true"`로 되돌려야 합니다(6번).
