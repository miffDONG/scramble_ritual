# 실제 입력 전처리 및 glyph 추출 가이드

`입력 전처리` 그룹은 camera/video/image 소스에만 적용된다. `시뮬레이션`과 `오브제(사운드)`는 비교 기준을 유지하기 위해 `전처리 전체 ON` 상태에서도 원래 렌더링을 사용한다(이 경우 캡션에 `PREPROCESS BYPASSED`가 뜬다).

각 단계는 독립적으로 켜고 끌 수 있으며 적용 순서는 다음과 같다.

```text
원본 → Percentile Autocontrast → Gamma → Bilateral → CLAHE → Unsharp
     → 기존 blur/조명 평탄화 → threshold → morphology open/close
```

## 원칙: 모든 옵션은 그림으로 확인한다

전처리와 추출 방식은 **눈으로 고르는 것**이지 숫자로 고르는 것이 아니다. 그래서 이 UI는 두 가지를 지킨다.

1. **모든 진단 화면은 영상 위에 그린다.** 파생 마스크를 순수 흑백으로 띄우면 contour는 선 맵을 아예 만들지 않아 새까만 화면이 되고, morphology는 기본 커널이 거의 모든 픽셀을 선으로 가져가 점 후보가 새까만 화면이 된다. 둘 다 피드백이 없는 것과 같다. 지금은 전처리된 grayscale을 어둡게 깐 위에 자홍(선)/초록(점)을 올린다.
2. **글자는 영상 아래 띠에 적는다.** 판단해야 할 픽셀 위에 글자를 겹치지 않는다. (cv2에 한글 폰트가 없어 캡션은 영문이다.)

## 모니터 탭

| 탭 | 내용 |
|---|---|
| `원본 \| 전처리` | 같은 프레임을 세로로 갈라 **좌=원본 / 우=전처리**. 같은 배율이라 경계선에서 미세한 대비 차이를 바로 본다. 위의 **분할 슬라이더**를 0%까지 밀면 전체가 전처리, 100%면 전체가 원본이라 슬라이더 하나가 전/후 전환이 된다 |
| `대비 강화` | 전처리가 끝난 grayscale 전체 |
| `추출 진단` | **고른 추출 방식이 실제로 한 일.** 픽셀 층(방식이 마스크를 어떻게 갈랐는지) + glyph 층(각 blob이 받은 선(1)/점(0) 판정과 그 판정을 만든 숫자) |
| `선 후보` | 선으로 분류된 픽셀을 영상 위에 자홍색으로 |
| `점 후보` | 후보 마스크에서 선을 뺀 나머지를 영상 위에 초록색으로 |
| `마스크` | threshold + open/close 직후의 후보 마스크 (순수 흑백) |
| `오버레이` | 최종 glyph, chain, ID 판독 결과 |
| `원본` | 입력 프레임 |

### `추출 진단` 읽는 법

- **자홍 사각형 + `1:값`** — 이 blob은 dash(1)로 읽힌다
- **초록 사각형 + `0:값`** — 이 blob은 dot(0)으로 읽힌다
- `값`은 판정을 만든 숫자다. Hough/Morphology에서는 **선 맵과의 겹침 비율**, Contour에서는 **aspect**
- 아래 캡션이 방식·파라미터·판정 규칙·최종 개수(`dash(1)=n dot(0)=m`)를 알려준다

판정 색은 `tracker/morse.py`의 `classify_slot`과 같은 순서를 따른다(형태 분류 → 선 맵 → 기하). 그림과 디코더가 어긋나면 그림이 잘못 가르치는 셈이라, 이 일치는 `tests/test_diagnostics.py`가 검사한다.

## 옵션은 선택된 것만 보인다

추출 방식은 셋 중 **하나만** 동작하므로, **고른 방식의 파라미터만** 패널에 나타난다.

| 선택 | 보이는 컨트롤 |
|---|---|
| `contour` | (전용 파라미터 없음 — 점/선 분류 그룹의 aspect 기준을 씀) |
| `hough` | 선 overlap 기준, Hough vote / 최소 선 길이 / 최대 선 간격 / 선 두께 |
| `morphology` | 선 overlap 기준, Morph 커널 길이 / 두께 |

전처리도 같다. `전처리 전체 ON`이 꺼져 있으면 하위 필터가 모두 숨고, 필터를 켜야 그 필터의 파라미터가 나타난다. **동작하지 않는 컨트롤은 보이지도 조작되지도 않는다** — 만져도 아무 일이 없는 슬라이더가 남아 있으면 그게 곧 오해의 원인이기 때문이다.

스키마에서는 `webui/schema.py`의 `show_when`이 이 규칙을 정의한다.

## 작은 모스용 권장 실험 순서

1. 이미지 소스를 선택하고 일시정지한다.
2. `원본 | 전처리` 탭에서 **분할 슬라이더를 좌우로 밀며** 전처리 효과를 확인한다.
3. `CLAHE`만 켜고 `clip limit=1.5~2.5`, `tile=8~16`을 비교한다.
4. 입자가 늘면 `Bilateral d=3~5`, `sigma=15~30`을 추가한다.
5. `마스크`에서 점이 유지되는 최소 threshold/blur/open 값을 찾는다.
6. `추출 진단` 탭을 켠 채 `Contour → Hough → Morphology`를 바꾸며 **사각형 색이 실제 카드의 점/선과 맞는지** 본다.

## 추출 방식별 시작값

| 방식 | 시작값 | 판단 기준 |
|---|---|---|
| Contour | 기존 aspect/area 설정 | 점 bounding box는 약 0.7~1.3, dash는 chain 축 방향으로 길어야 함 |
| Hough | vote 6~12, 최소 길이 4~8px, gap 2~4px | `선 후보`에 dash 중심선은 남고 원형 dot은 남지 않아야 함 |
| Morphology | 커널 길이 7~11px, 두께 1px | 커널 길이는 dot 지름보다 크고 dash 길이보다 작아야 함 |

Hough와 Morphology에서는 `선 overlap 기준` 이상으로 line mask와 겹치는 glyph를 dash(1), 나머지를 dot(0)으로 판정한다. `추출 진단`에서 **전부 자홍**이면 커널/최소 선 길이가 너무 작아 모든 blob이 선으로 잡힌 것이고(기본 morphology 커널 9px가 흔히 그렇다), **전부 초록**이면 반대다. 실제 dash에만 자홍이 남을 때까지 커널 길이 → overlap 기준 순으로 올린다.

전처리는 대비를 높일 뿐 아크릴 경계와 실제 모스를 의미적으로 구분하지 않는다. 따라서 실제 설치에서는 ROI를 테이블로 제한하고, 가능하면 다음 단계에서 삼각 오브제 내부 ROI를 별도로 검출해 그 안에서만 chain을 찾는 것이 안전하다.
