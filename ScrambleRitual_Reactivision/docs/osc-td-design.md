# TD용 OSC 데이터 설계

작성일: 2026-10-06
수정일: 2026-10-07

이 문서는 SOUND 및 TD 데이터 구조와 처리 규칙을 기록한다. obj 인식 수명, 접촉 간선 유지 MST + max, pairId, heartbeat, SOUND/TD 전송을 구현했다. 그룹 기능은 `# 미구현`에 보류한다. margin의 현장 보정과 실제 TD 수신 검증은 별도 현장 설정 작업이다.

## 목적

현재 전송 범위는 개별 obj 위치와 tension, 대표 연결이다. tension 1.0 집단의 그룹 계산·별도 포트 전송은 보류한다. TD에서 TOP과 POP을 조합해 교집합 면적을 찾고 하나의 큰 세포로 표현하는 방향을 검토한다. 기존 그룹 설계는 아래 `# 미구현`에 보존한다.

## obj 인식과 수명

- 고유 obj ID는 0~24이며 각 ID의 마커는 하나씩 사용한다.
- 최초 인식은 즉시 등록하고 OSC를 전송한다. 최초 인식에 유지 트리거를 두지 않는다.
- 전송 목록은 최초 인식 순서로 유지한다. 새 obj는 끝에 추가하고, 소실 확정된 obj는 해당 위치에서 제거한다. 위치 변화로 재정렬하지 않는다.
- 중간 항목을 제거하면 남은 항목의 상대적인 순서는 유지된다. 목록 슬롯 번호는 고유 ID가 아니다.
- 연속 5프레임 미인식이면 소실로 판단한다. 100fps에서 0.05초이며, 시간 고정이 아닌 프레임 기준이다.
- 유예 중 재인식되면 미인식 카운터를 초기화하고 기존 목록 위치를 유지한다.
- 소실 확정 후 재등장하면 목록 끝에 추가한다.
- ROI 밖에도 같은 소실 유예 기준을 적용한다.
- 소실 유예 중에는 마지막 관측값을 유지해 전송한다.
- obj 전송, MST, tension, pairId는 동일한 유지 obj 목록을 사용한다. 제거와 관계 재계산은 동일 프레임에 반영한다. 향후 그룹 기능을 재개하면 같은 목록을 사용한다.

예: `[5, 3, 12]`에서 3이 소실 확정되면 `[5, 12]`, 이후 7이 인식되면 `[5, 12, 7]`, 3이 재등장하면 `[5, 12, 7, 3]`이다.

## tension과 연속 보정

- 거리 기준은 테이블 ROI 장변으로 정규화한 중심거리다.
- tension 0 도달 거리는 테이블 장변의 절반인 `d_far = 0.5`다.
- obj tension은 MST 이웃과의 보정된 pair tension 중 최댓값(max)이다. avg를 사용하지 않는다.
- 접촉 상태의 중심 흔들림으로 0.99와 1.0이 반복되는 것을 줄이면서, 1.0 직전의 연속 값과 1.0에서 안정화되는 효과를 유지한다.
- `raw >= 0.98 → 1.0` 같은 값 치환은 사용하지 않는다. 0.98, 0.99가 출력 가능한 연속 곡선을 사용한다.

거리 곡선 보정안:

```text
d_contact = d_near + margin

dist <= d_contact : 1.0
dist >= 0.5       : 0.0
그 사이           : (0.5 - dist) / (0.5 - d_contact)
```

`d_near`는 기존 접촉거리 기준이고, `margin`은 접촉 상태에서 측정되는 거리 노이즈를 흡수하기 위한 보정량이다. `0 <= d_contact < 0.5`를 만족해야 한다. 기본 보정량은 0.012(테이블 장변의 1.2%)이며 실제 환경에 맞춰 조정할 수 있다. 1280px 장변에서는 약 15.4px만큼 1.0 도달 중심거리를 넓힌다. 대표 연결 판정에는 이 보정 곡선을 사용한다.

## 중요: MST와 1.0 연결의 안정성

pairId 후보는 MST 이웃이다. 전체 obj에서 별도로 대표 상대를 고르는 방식은 사용하지 않는다.

매 프레임 거리만으로 MST를 새로 만들면 여러 쌍이 tension 1.0인 상태에서 미세한 거리 변화로 기존 간선이 빠질 수 있다. pairId 동률 유지 규칙만으로는 이 문제를 해결할 수 없다. 따라서 구현 시 다음 유지 규칙을 반영해야 한다.

1. 이전 MST 간선 중 양쪽 obj가 유지 중이고 보정 tension이 계속 1.0인 간선을 우선 유지한다.
2. 유지 간선으로 연결되지 않은 부분을 거리 기준으로 연결하여 트리를 완성한다.
3. 각 obj는 완성된 MST의 이웃 중 최대 보정 tension 상대를 선택한다.
4. 기존 pairId가 최대 tension 후보라면 유지한다. 특히 여러 이웃이 1.0이면 처음 선택된 상대를 유지한다.
5. 기존 상대가 소실되거나 최대값 후보에서 벗어나면 남은 MST 이웃에서 재선정한다.

유지 간선을 우선하므로 매 순간 총거리가 최소인 엄밀한 MST와 차이가 날 수 있다. 이 선택은 1.0 구간의 연결 안정성과 TD 비주얼 연속성을 위한 것이다.

최초 선택 및 재선정 시 tension 동률은 중심거리가 가까운 이웃을 우선하고, 거리도 같으면 고유 ID가 작은 이웃을 선택한다. 이미 선택된 상대가 최대 tension 후보이면 이 순서보다 기존 상대 유지가 우선한다. 노드별 간선 수 상한은 두지 않으며 전체 트리의 간선 수는 N−1이다.

## pairId 의미와 -1 사례

pairId는 대표 이웃의 고유 obj ID를 참조한다. 목록 슬롯이나 별도 pair 식별자가 아니다. 각 obj의 선택은 비대칭일 수 있으므로 `A → B`가 `B → A`를 보장하지 않는다.

무방향 MST에서 리프 노드도 이웃이 하나 있으므로 리프라는 이유만으로 pairId가 -1이 되지는 않는다.

- 유지 obj가 혼자여서 MST 이웃이 없으면 -1이다.
- MST 이웃의 보정 tension이 모두 0이면 -1이다.
- 기존 상대가 소실되면 재선정하며, 남은 이웃이 없거나 모두 tension 0이면 -1이다.
- 0보다 큰 tension에 대해 별도 후보 거리 제한은 두지 않는다.

## SOUND 전송 규약: `/scramble/obj`

SOUND 프로그램에는 기존 obj당 키·값 교대 메시지를 활성 규격으로 유지한다. TD 전송 양식 추가로 이 규격을 대체하지 않는다. obj에 groupId는 넣지 않는다.

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| id | int | 고유 obj ID, 0~24 |
| bits | string | id의 8비트 이진 표기 |
| x | float | ROI 폭 기준 정규화 위치 |
| y | float | ROI 높이 기준 정규화 위치 |
| tilt | float | 기존 각도 규약, 도 단위 |
| tension | float | 보정된 MST 이웃 tension의 max, 0~1 |
| pairId | int | 대표 MST 이웃의 고유 ID, 없으면 -1 |
| heartbeat | int | 해당 계산·송신 프레임의 순환 번호, 0~100 |

```text
["id", 5, "bits", "00000101", "x", 0.5964, "y", 0.4421,
 "tilt", 100.64, "tension", 1.0, "pairId", 3, "heartbeat", 20]
```

## TD 전송 규약

이 규약은 TD 대상에만 적용한다. SOUND와 같은 프레임에서 계산한 동일한 obj 데이터와 타입을 사용하며 전송 표현만 추가한다. 사운드 등 다른 수신 대상의 기존 형식과 필드명을 변경하지 않는다.

### 필드명 + 세포 목록 번호

TD 채널 이름은 `obj1`, `obj2`가 아니라 `id1`, `x1`, `y1`, `tilt1`, `tension1`, `pairID1`, `id2`, ... 형식으로 구성한다. 목록 번호는 1부터 시작하며, 인식 순서로 유지되는 현재 목록의 위치다. 고유 ID 값은 계속 0~24다.

- 유지 목록이 `[5, 3, 12]`이면 `id1=5`, `id2=3`, `id3=12`다.
- 3의 소실이 확정되어 `[5, 12]`가 되면 `id1=5`, `id2=12`다. 뒤 슬롯은 당겨지며 목록 번호를 영구 식별자로 사용하지 않는다.
- pairID의 값은 상대의 고유 ID다. 상대의 목록 번호로 변환하지 않는다.
- 각도 필드는 기존 명칭인 `tilt`를 사용한다. 요청 예시의 `tit`는 `tilt`로 정리한다.
- 내부 대표 연결 명칭은 pairId를 유지하되 TD 채널 명칭은 요청한 `pairID`로 표기한다.

### 채널 이름을 OSC 주소로 전달

키 문자열을 `/scramble/obj` 메시지의 인자로 나열하는 것만으로는 원하는 채널명이 생성된다고 보장할 수 없다. 따라서 TD용 전송은 **필드별 OSC 주소 + 원래 타입의 인자 하나**로 표현한다. SOUND의 키·값 교대 메시지는 그대로 유지한다. TD에도 bits를 문자열로 포함하며 필드를 삭제하거나 타입을 변환하지 않는다.

### 프레임당 하나의 OSC bundle

해당 프레임의 모든 obj 필드 메시지를 인식 목록 순서로 하나의 OSC bundle에 담아 TD obj 수신 포트로 한 번 전송한다. obj별 또는 필드별로 별도 UDP 송신하지 않는다. 아래 줄들은 개별 패킷이 아니라 같은 bundle 안의 OSC 메시지들이다. bundle은 즉시 처리하도록 전송한다.

```text
/scramble/id1        5
/scramble/bits1      "00000101"
/scramble/x1         0.5964
/scramble/y1         0.4421
/scramble/tilt1      100.64
/scramble/tension1   1.0
/scramble/pairID1    3
/scramble/heartbeat1 20

/scramble/id2        3
/scramble/bits2      "00000011"
/scramble/x2         0.62
/scramble/y2         0.45
/scramble/tilt2      0.0
/scramble/tension2   1.0
/scramble/pairID2    5
/scramble/heartbeat2 20
```

프레임마다 목록 1번의 필드를 위 순서로 bundle에 넣고 다음 목록 번호로 진행한다. SOUND와 TD는 같은 id, bits, x, y, tilt, tension, pairId, heartbeat 값을 받는다. TD의 pairID 표기는 필드명 표현 차이일 뿐 값과 의미는 같다.

TD의 OSC In CHOP에서 `Strip Prefix Segments = 1`로 `/scramble` 프리픽스를 제거하여 `id1`, `x1` 등의 숫자 채널명을 사용한다. bitsN은 문자열이므로 OSC In DAT에서 문자열로 읽는다. 수신 경로 구성은 TD에서 확인하며 송신 측에서 bits를 숫자로 바꾸지 않는다.

하나의 bundle은 한 UDP 데이터그램으로 송신하지만 TD 내부의 모든 필드 동시 적용까지 보장하는 규약은 아니다. 전체 obj bundle 크기는 구현 시 확인한다. 일반 LAN의 MTU를 초과하면 IP 단편화가 발생할 수 있으므로 프레임당 한 번 송신은 패킷 크기를 줄이는 것과 다르다.

참고: [TouchDesigner OSC In CHOP 공식 문서](https://docs.derivative.ca/OSC_In_CHOP)

| TD 채널 패턴 | 타입 | 의미 |
| --- | --- | --- |
| idN | int | 고유 obj ID, 0~24 |
| bitsN | string | SOUND와 동일한 id의 8비트 이진 표기 |
| xN | float | ROI 폭 기준 정규화 위치 |
| yN | float | ROI 높이 기준 정규화 위치 |
| tiltN | float | 기존 각도 규약, 도 단위 |
| tensionN | float | 보정된 MST 이웃 tension의 max, 0~1 |
| pairIDN | int | 대표 MST 이웃의 고유 ID, 없으면 -1 |
| heartbeatN | int | 0~100 순환 값. 같은 프레임의 모든 목록 번호에 동일한 값 사용 |

TD 전송에도 SOUND의 모든 obj 필드를 포함한다. 목록 번호 접미사와 pairID 표기 외에는 값과 타입을 변경하지 않는다.

heartbeat는 0부터 시작해 송신 프레임마다 1씩 증가하고, 100 다음에는 0으로 돌아간다. 각 필드 전송마다 증가시키지 않는다. 프로그램의 전송 지속 여부와 obj별 갱신 상태를 확인하는 용도이며 전체 메시지 수신 완료를 보장하지 않는다.

별도의 프레임 헤더, end 메시지, objCount 메시지는 추가하지 않는다. 줄어든 목록의 남은 TD 채널은 heartbeatN 갱신 여부로 만료 처리하는 방향이며 구체적인 수신 타임아웃은 TD에서 정한다. 모든 obj가 없으면 heartbeat도 오지 않는다는 제한이 있다.

## 현재 설계의 현장 설정 항목

- 접촉거리 보정 margin의 측정값.
- TD obj 수신 포트 번호와 OSC 주소의 채널명 해석 설정.
- 소실 후 남은 TD 채널의 만료 시간. 서버의 5프레임 소실 유예와 별개인 수신 측 설정이다.

위 항목을 이유로 기각된 프레임 헤더나 종료 메시지를 임의로 추가하지 않는다.

# 미구현

아래는 기존 그룹 설계를 보존한 내용이다. 현재 구현·전송 범위에서 제외하며, 삭제하거나 구현 완료로 간주하지 않는다. 그룹 생성·유지·소멸 처리를 포함한 tension 1.0 그룹 기능과 별도 포트 송신은 보류한다.

## 그룹 (보류)

- 보정 pair tension이 1.0인 연결을 통해 이어진 obj들의 연결 성분을 그룹으로 정의한다.
- 구성원이 2개 이상인 집단을 그룹으로 전송한다.
- 대표 pairId만으로 그룹을 구성하지 않는다. 대표 상대 선택에서 빠진 접촉 연결도 그룹 판정에 반영한다.
- groupId는 현재 프레임 안에서 유효한 참조다. 프레임 간 동일 ID 유지 의무는 없다.
- 구성원 목록은 집합을 뜻한다. 모든 구성원이 서로 직접 접촉한다거나 목록 순서대로 연결된다는 뜻은 아니다.
- 그룹 중심은 구성원 중심좌표의 산술평균이다.
- centerX, centerY는 obj x, y와 같은 ROI 좌표 기준을 사용한다.
- 생성 및 유지 중인 모든 그룹을 매 프레임 전송한다.

## 그룹 전송 규약 (보류)

그룹 기능 재개 시 별도 UDP 포트에서 아래 형식을 사용한다. 현재 SOUND 및 TD obj 전송 규약을 대체하지 않는다.

### group 포트: `/scramble/group`

그룹 하나당 메시지 하나를 전송한다. obj와 동일한 키·값 교대 형식을 사용한다. 구성원 고유 ID는 `objlist` 키의 쉼표 구분 문자열로 전달한다. 공백 없이 작성하며 목록 슬롯 번호가 아닌 실제 고유 obj ID를 사용한다.

```text
["groupId", 2, "memberCount", 4, "objlist", "3,7,12,20",
 "centerX", 0.45, "centerY", 0.62, "heartbeat", 20]
```

위 예시의 heartbeat는 20, groupId는 2, 구성원은 4개, 중심은 `(0.45, 0.62)`, 구성원 ID는 `[3, 7, 12, 20]`이다. memberCount는 해당 그룹의 구성원 수이며 전체 그룹 수가 아니다.

TD는 OSC In DAT의 Split Message into Columns를 사용해 각 인자를 개별 열로 받을 수 있다. obj와 group 모두 키·값 쌍으로 해석한다. `objlist` 문자열을 쉼표로 분리하고 각 항목을 정수로 변환하여 구성원 고유 ID 목록을 얻는다. memberCount는 이 목록의 구성원 수와 일치한다. 중첩 OSC 배열은 사용하지 않는다.

참고: [TouchDesigner OSC In DAT 공식 문서](https://docs.derivative.ca/OSC_In_DAT)

## 그룹 재개 시 검토 항목 (보류)

- obj–group 및 group–group의 거리/tension 기준과 전송 구조.
- 그룹 중심거리와 구성원 간 최근접거리의 활용. 거리 계산은 x/y 각각의 정규화 차이를 고려하여 테이블 장변 기준을 사용한다.
- 접촉거리 보정 margin의 현장 측정값.
- 최초 pairId 선택 및 재선정의 동률 결정 순서.
- obj/group 포트 번호.
- 프레임 헤더 없이 그룹 소멸·그룹 0개·obj 0개를 TD에서 처리하는 규약. 메시지가 하나도 없으면 heartbeat도 전송되지 않으므로 무대상이 된 상태와 송신 중단을 heartbeat만으로 구분할 수 없다.
- 별도 포트의 동일 heartbeat 데이터를 TD에서 적용하는 시점과 누락 시 처리. heartbeat만으로는 해당 프레임의 모든 그룹이 도착했는지 알 수 없다.

위 미정 항목을 이유로 기각된 프레임 헤더나 종료 메시지를 임의로 추가하지 않는다.
